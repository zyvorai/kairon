## v0.5+

- [x] PVC -> FluxVM disk lifecycle (first cut): `spec.volumes[0]` boots from a Bound PVC's `hostPath`/`local` PersistentVolume — see `docs/guides/machine-storage.md`. Still open: multiple volumes per Machine.
- [x] CSI node-plugin integration for network-block volumes (first cut, one backend): `csiNode.enabled` deploys Kairon's own iSCSI-only CSI node plugin (`internal/csinode`, no Controller service, no dynamic provisioning -- PVs are static). The second deliberate exception to Go-stdlib-only (`google.golang.org/grpc`, `github.com/container-storage-interface/spec`) -- the CSI protocol itself has no stdlib-only wire format. `kairon-node` dials it directly as its own CSI client rather than through kubelet's Pod volume machinery, since a Machine has no backing Pod. No Ceph/EBS/other backends, no CHAP on Kairon's own consumption path, no volume expansion. Runs privileged, on a non-distroless base image. See `docs/guides/machine-storage-csi.md`.
- [x] `MachineSnapshotRestore` (first cut): restores one `MachineSnapshot` volume into a new PVC via the standard CSI `dataSource` flow — "restore" and "clone-from-snapshot" are the same operation in Kubernetes' storage model, so this covers both. Deliberately doesn't also create a Machine (point the existing PVC-backed-disk feature at the result instead) — see `docs/guides/machine-snapshot-restore.md`. Needs a real CSI snapshotter behind your StorageClass (confirmed on a real cluster: Rancher's `local-path-provisioner` doesn't have one -- "snapshotting non-CSI volumes is not supported").
- [x] CPU/memory hotplug (first cut): growing `spec.resources` on a Running Machine calls FluxVM's real QMP hotplug (`device_add`/`object-add`, shipped upstream in FluxVM's own `feat/qemu-cpu-memory-hotplug`, PR #62) — see `docs/guides/machine-hotplug.md`. Grow-only (no CPU/DIMM unplug), bounded by headroom reserved automatically at creation (not yet Kairon-configurable), lost across any Machine re-realization (stop/start, cold migration).
- [x] guest-agent (qemu-guest-agent) integration: `spec.guestAgent.enabled` resolves `status.guestIP` via FluxVM's real `guest-network-get-interfaces` (shipped upstream, [zyvorai/fluxvm#63](https://github.com/zyvorai/fluxvm/pull/63)) for network modes with no DHCP lease file (`user`/SLIRP in particular) — see `docs/guides/machine-guest-agent.md`. Graceful-shutdown wiring turned out to be unnecessary: FluxVM's `stop`/`delete` already does ACPI `system_powerdown` with a wait-then-force fallback regardless of guest agent presence. Multi-NIC/IPv6 (`status.guestIPs`) and periodic re-resolution (every 5 minutes once first resolved, instead of once-ever) closed the two gaps this used to list as still open.
- [x] Machine affinity/anti-affinity: `spec.placement.affinity`/`antiAffinity` (required/hard) gate scheduling against other Machines' current placement. Since v0.5, `internal/scheduler` also does real weighted scoring on top of the existing least-loaded/hash-tiebreak baseline: `preferredAffinity`/`preferredAntiAffinity` (soft, weighted), `topologySpreadConstraints` (soft, minimizes matching-Machine count per topology domain; `maxSkew` is also hard-enforced per constraint via `whenUnsatisfiable: DoNotSchedule`, mirroring the Kubernetes field), and a best-effort DRA topology-awareness hint (reads back an already-allocated `ResourceClaim`'s device pool via `ResourceSlice.spec.nodeName`, no role in allocation itself). A Machine using none of the new fields schedules identically to before this scoring pass existed. See `docs/guides/machine-placement.md`.
- [x] `MachineDisruptionBudget`: `evacuate` throttles itself against `minAvailable`/`maxUnavailable` instead of migrating an entire node at once — see `docs/guides/machine-disruption-budgets.md`. Since v0.5, an opt-in validating admission webhook (`webhook.enabled`) also rejects a `MachineMigration` created directly through the API if it would violate a budget — closing the "only gates `kaironctl evacuate`" gap this line used to describe. `kairon-controller` now also reconciles real `status` (`expectedMachines`/`currentHealthy`/`desiredHealthy`/`disruptionsAllowed`) every tick, mirroring a real PodDisruptionBudget's status and closing what used to be documented as "no live status, no controller for this object" — purely observational, `evacuate`/the webhook still each recompute their own allowance fresh rather than trusting it. `evacuate --wait` now keeps retrying (matching `kubectl drain`'s own retry model) until the node is actually empty or `--timeout` elapses, instead of a single pass that left budget-blocked Machines behind for good -- the closest thing to an automatic node-drain Kairon has, deliberately still operator-invoked rather than triggered by `node.spec.unschedulable` on its own.
- [x] `MachineQuota` (namespace-scoped): `maxMachines`/`maxTotalCpu`/`maxTotalMemory`, enforced in `kairon-controller`'s scheduling loop — see `docs/guides/machine-quotas.md`. Since v0.5, the same opt-in webhook above also rejects a `Machine` create that would immediately exceed a quota (matching the reconcile loop's own CREATE-only scope), instead of only leaving it `Pending` — and now also rejects an update that hotplug-resizes an already-scheduled Machine's `spec.resources` past quota, closing what was a real, documented gap (`kairon-node`'s hotplug reconciliation has no cluster-wide quota visibility of its own, so this is the one quota check with no reconcile-loop equivalent to backstop it). `migration.maxConcurrentPerNode`/`maxConcurrentCluster` (a per-node/cluster concurrency cap on in-flight migrations specifically) remains a separate, narrower control this doesn't replace.
- [x] `kairon-ui` in-place password management: self-service change + admin reset (`POST /api/v1/auth/password`, `POST /api/v1/users/{username}/password`), replacing "regenerate a bcrypt hash and redeploy" for named `ui.auth.users` accounts.
- [x] `scripts/deploy-remote.sh --console-tls`: automates (or accepts bring-your-own) TLS material for the kairon-ui↔kairon-node console relay hop, previously a manual step.
- [x] Helm chart hardening: `PodDisruptionBudget` (on by default) and opt-in `NetworkPolicy` for `kairon-controller`/`kairon-ui`.
- [x] Supply chain: Dockerfile base images pinned to a digest, Trivy image scanning in CI, and a tag-triggered `release.yml` that publishes scanned, digest-pinned images to `ghcr.io/zyvorai/kairon-*` — this repo's CI is now the source of those tags.
- [x] SR-IOV/GPU migration capability checks (preflight only, first cut): `internal/controller/preflight.go`'s `deviceClaimsPreflight` refuses live migration of a `spec.deviceClaims` Machine outright -- VFIO passthrough is boot-time-only, and QEMU's live-migration RAM transfer fundamentally cannot carry a passthrough PCI device's in-flight state across hosts without a hot-unplug/hot-plug bracket FluxVM doesn't expose today (it has `HotplugCPU`/`HotplugMemory` but no VFIO equivalent) -- turning a previously silent gap (the device was just left behind) into an explicit, honest rejection instead. Cold migration is allowed when the target node asserts an equivalent device via the new opt-in `kairon.zyvor.dev/vfio-devices` label (the same "operator-asserted, can only confirm a mismatch" honesty `storage-domain`/`network-domain` labels already have) -- cold migration has no state-transfer problem, since the guest is stopped and a fresh runtime created at the target exactly like initial creation. Actually carrying a device through *live* migration remains blocked on FluxVM gaining real VFIO hot-unplug/hot-plug support -- a genuine upstream dependency, not an unpicked Kairon TODO.
- [x] Guest quiesce hooks for snapshots (first cut): a Machine with `spec.guestAgent.enabled` now gets a real `guest-fsfreeze-freeze`/`guest-fsfreeze-thaw` around `MachineSnapshot`'s VolumeSnapshot creation, for an application-consistent snapshot instead of a merely crash-consistent one -- the same mechanism libvirt/virt-manager already use. This needed new support on both sides: FluxVM itself had no `fsfreeze` endpoint at all (its QGA surface was narrow and purpose-built -- network-interfaces, exec, firewall -- though it already had the low-level `qga::raw` plumbing this reuses), so `POST /v1/vms/{id}/qga/fsfreeze`/`fsthaw` were added there first. On Kairon's side, `kairon-controller` (which reconciles `MachineSnapshot`) has no network path to a Machine's FluxVM instance at all -- only `kairon-node` does -- so freeze/thaw is coordinated via a request/response annotation pair on the Machine itself (`kairon.zyvor.dev/quiesce-request`/`quiesce-status`, `internal/controller/snapshot.go` + `internal/agent/quiesce.go`), the same "durable request in the API, not memory" pattern `kairon.zyvor.dev/adopt-only` already established for controller↔node coordination during live migration. A freeze that never confirms within 30s falls back to an unquiesced, crash-consistent snapshot rather than blocking forever; a thaw that fails is retried indefinitely, never silently abandoned, matching `NeedsRecovery`'s own posture. QEMU backend only. See `docs/guides/machine-snapshot-quiesce.md`.
- Cluster API infrastructure provider ("Kubernetes clusters made of Kairon Machines") -- scoped, not built: this is a separate project (its own controller-manager/repository/release, following `cluster-api-provider-<name>` convention), not a Kairon feature PR. Real blocker, not just size: CAPI's whole object graph is built on `metadata.ownerReferences`, confirmed absent everywhere in this codebase (`model.ObjectMeta` has no such field; every parent-child relationship today is a plain name/label reference the reconcile loop resolves itself, e.g. `MachineSet`'s own template-hash label). Two real fits worth keeping if this is ever built: CAPI bootstrap-data Secrets could plausibly forward straight into `spec.cloudInit` with little new plumbing, and `MachineSet`'s own "create/delete to match a template" reconciliation shape is conceptually close to what CAPI expects from an infra provider. See `docs/design-cluster-api-provider.md`.
- [x] TLS certificate hot-reload (`internal/tlsreload`): migration mTLS, the VNC console relay, and the admission webhook all now pick up a renewed leaf certificate/key (e.g. from cert-manager) within 30s, no restart. Only the leaf cert/key -- a CA bundle still loads once at startup. Automated issuance (ACME/cert-manager integration Kairon itself drives) and SPIFFE-style workload identity remain open.
- [x] node fencing (first cut): `kairon-controller` sets a `NodeUnreachable` condition on any Machine whose node stops being `Ready`, every reconcile tick -- detection only, never automatic rescheduling (risks running the same VM twice). `kaironctl fence --reason ...` is the explicit operator-attested action that clears a Machine for rescheduling once a human has confirmed out-of-band the node is truly gone -- see `docs/guides/machine-fencing.md`.
- confidential VM policy (SEV-SNP/TDX) -- verified, majority blocked upstream: the same root cause as `spec.security.secureBoot`/`.tpm` above (confirmed against FluxVM's own source, not assumed -- zero references to SEV/SNP/TDX/confidential-computing anywhere in its crates, the same "no firmware/attestation support at all" gap). Deliberately not adding a new `spec.security` field for this yet: unlike `secureBoot`/`.tpm` (pre-existing fields nobody knew were dead), inventing API surface specifically so it can always be rejected would be speculative, not a real capability with a real caller behind it. Revisit once FluxVM has real SEV-SNP/TDX support to expose.
- [x] OIDC/SSO for `kairon-ui` (first cut): `ui.oidc.enabled`, Authorization Code + PKCE against an external identity provider, alongside `ui.auth.users`. The one deliberate exception to Kairon's Go-stdlib-only design (`golang.org/x/oauth2`, `github.com/coreos/go-oidc/v3`) -- real JWT/JWK verification isn't something to hand-roll. No group-to-admin claim mapping, no SP-initiated single-logout, no refresh-token renewal. See `docs/guides/kairon-ui-oidc.md`.
- [x] multi-replica `kairon-ui` (first cut): `ui.replicaCount > 1` propagates session revocation, login lockout, console tickets, and password changes across replicas via a shared, Kubernetes-native `ConfigMap` (deliberately not Redis) -- eventually-consistent (~15s), not instant; login-lockout's failure count is per-replica, not one cluster-wide atomic counter; concurrent password changes to two different accounts on two different replicas can still race. See `docs/guides/kairon-ui-ha.md`.
- [x] `kairon-controller` HA (first cut): `controller.replicaCount > 1` closes what was previously this project's clearest single point of failure -- a `coordination.k8s.io/v1` Lease (`internal/leaderelection`, hand-rolled on top of `internal/kube` rather than pulling in `client-go`'s leader-election package) ensures only the elected leader's reconcile loop runs at a time; the admission webhook and health/metrics endpoints are unaffected, serving from every replica regardless. On by default in the Helm chart even at `replicaCount: 1`; off by default at the binary/flag level for backward compatibility with existing bare-metal deployments. Takeover after a lost leader costs up to ~15s, not instant. See `docs/guides/kairon-controller-ha.md`.
- [x] upgrade/scale/failure-injection test suites (first cut): `internal/integration` (already home to the controller+agent migration pipeline test) gains three more real, in-process suites, each driving actual reconcile loops rather than mocking around them. **Scale** (`scale_test.go`): a `MachineSet` scaled 0→12→5 through `Controller.Reconcile`'s real, full multi-concern loop (not `reconcileMachineSet` called directly, which `internal/controller/machineset_test.go` already covers in isolation) -- proving created replicas actually flow through scheduler assignment to real nodes, evenly. **Failure injection**: a fake Kubernetes API server that fails a MachineSet's first create call once (`scale_test.go`) proves the fault surfaces in `status.message` and the next tick makes up the shortfall with no duplicates; a fake FluxVM that goes fully unreachable (`failure_injection_test.go`, covering both of `Agent.current`'s ID- and name-lookup paths together, since either alone is already masked by the other's fallback) proves a Machine surfaces `Error`/`Ready=False` during the outage and recovers to `Running` on its own the next tick, no operator action needed. **Upgrade** (`internal/model/compat_test.go`): a Machine JSON blob in an older, pre-this-session shape (missing every field added since) still decodes cleanly, and one in a hypothetical *newer* shape (extra fields this binary doesn't know about yet) decodes and round-trips without leaking or losing anything -- the real backward/forward-compatibility guarantee `docs/guides/crd-versioning.md` describes but had never been asserted in code. Building the FluxVM-outage test caught a real, separate latent bug along the way, fixed in the same commit: `MachineStatus.Message` and six sibling status `Message` fields were tagged `omitempty`, which silently dropped the field from every JSON merge-patch once a reconcile tried to clear it back to `""` -- RFC 7386 treats an *absent* key as "leave unchanged," not "clear," so a recovered Machine/Migration/Snapshot/etc. would have kept showing its last error message forever. Now covered by its own direct regression test (`TestStatusMessageFieldsAlwaysSerialize`), not just caught incidentally. Real limits: no upgrade test yet exercises an actual live Kubernetes API server's own CRD schema validation (`kubectl apply` of an old/new object against the real `openAPIV3Schema`) or a real Helm-chart `helm upgrade`; scale is proven into the low tens of Machines, not load-tested at production scale; failure injection covers FluxVM-unreachable and one apiserver-create-failure shape, not every possible fault (e.g. a slow/timing-out apiserver, a partial write).
- [x] Backup/restore for Kairon's Kubernetes-level state (first cut): `scripts/backup-crds.sh`/`restore-crds.sh` back up and restore the eight `kairon.zyvor.dev` CRD kinds, plus opt-in chart-managed Secrets -- closing what was previously a real, undocumented gap (no backup/DR story existed at all). Restoring a Machine whose FluxVM runtime is still alive re-adopts it by name (`RuntimeName()`, not `status.runtimeID`); if the runtime is also gone, a fresh VM is created from `spec.image`/`spec.resources` instead -- whether that's a real recovery depends on whether the boot disk itself survived independently. Does not cover VM disk content (the CSI driver's/storage backend's job) or FluxVM's own per-host state. See `docs/runbook-backup-restore.md`.
- [x] Observability beyond migrations (first cut): Prometheus metrics used to be `kairon-controller`-only and migration-lifecycle-only -- no signal at all if the controller was unhealthy or wedged, no metrics from `kairon-node`/`kairon-ui` at all. Now every component exposes `kairon_apiserver_request_duration_seconds` (every `internal/kube.Client` call, by method/outcome); `kairon-controller`/`kairon-node` also expose `kairon_reconcile_duration_seconds`/`kairon_reconcile_errors_total`; `kairon-controller` also exposes `kairon_webhook_decisions_total` when `webhook.enabled`; `kairon-ui` exposes its own `kairon_ui_request_duration_seconds`. Three new alerts (`charts/kairon/alerts.yaml`'s `kairon-health` group) on reconcile error rate, apiserver error rate, and webhook deny-rate spikes -- the `PrometheusRule` this optionally renders is renamed `kairon-alerts` (from `kairon-migrations`) to match, see `docs/guides/observability.md`.
- [x] `kairon-ui` per-address rate limiting (first cut): every route now bounds request volume per remote address (`-rate-limit-rps`/`-rate-limit-burst`, on by default), via a new hand-rolled `internal/ratelimit` token bucket -- stdlib-only, so this didn't need a third exception to Go-stdlib-only after OIDC and CSI. Distinct from, and in addition to, the existing per-username login lockout: this bounds volume from one client address against *any* route, not just repeated failed passwords against one username. Deliberately doesn't cover the admission webhook (would risk rejecting a legitimate bulk `kubectl apply` under `failurePolicy: Fail`) or inter-component RPCs (already mTLS/bearer-token-restricted to trusted peers, not open to arbitrary traffic). Keyed by `r.RemoteAddr` alone -- collapses to one bucket for every client behind a load balancer with no `X-Forwarded-For` trust configured, a real known limit. See SECURITY.md.
- [x] Per-Machine VNC console authorization (first cut): the opt-in `kairon.zyvor.dev/console-allowed-users` annotation (comma-separated operator usernames) closes what was previously an all-or-nothing model -- any operator who could see a Machine could open its console. Unset (the default) is unchanged; set, `handleConsoleTicket` denies ticket issuance to anyone not listed, with an admin account (`ui.auth.users[].admin`) always able to bypass it for break-glass access, and a caller with no real per-operator identity (the legacy shared `ui.token`, or unauthenticated dev mode) denied outright rather than silently allowed. Bundled with a fix to bind each console ticket to the one Machine it was issued for -- without it, a ticket for a Machine the caller can access could be replayed against one they can't, within the ticket's 30s TTL. FluxVM's own VNC socket remains unauthenticated as-is; this closes the authorization gap at the kairon-ui layer, not the underlying trust chain. See SECURITY.md's "VNC console" section.
- [x] CRD conversion webhook scaffold (first cut): new `internal/conversion` hand-rolls the `apiextensions.k8s.io/v1` `ConversionReview` wire format, the same kind of deliberate exception `internal/admission` already makes for `AdmissionReview` -- no client-go dependency. `kairon-controller`'s existing webhook server exposes a tested `POST /convert/machinequotas` on the same TLS listener/certificate/`Service` as the admission webhook, backed by a real worked example (`ConvertMachineQuota`: renames `MachineQuota.spec.maxTotalCpu`/`maxTotalMemory` and the matching `status` fields to `maxCpu`/`maxMemory` between a hypothetical `v1beta1` and today's `v1alpha1`), proven via unit tests and a real end-to-end HTTP `ConversionReview` test. No CRD actually registers a second version yet -- this is infrastructure ready to wire in, not a live version bump; it also names, rather than solves, one real remaining gap: `charts/kairon/crds/*.yaml` lives in Helm's never-templated `crds/` directory, so a live `caBundle` for a real `spec.conversion` needs a deliberate follow-up choice. See `docs/guides/crd-versioning.md`.
- [x] Real Kubernetes RBAC for console access (first cut): `ui.auth.rbacConsoleCheck` (opt-in) layers a real `authorization.k8s.io/v1` `SubjectAccessReview` (verb `get` on the `machines/console` subresource) on top of the existing `kairon.zyvor.dev/console-allowed-users` annotation allowlist -- closing a real gap versus KubeVirt's aggregated-API-server subresource RBAC, without any CRD changes (`kubectl create clusterrole --resource=machines/console --verb=get` already works today; RBAC resource strings with a subresource suffix are just strings the authorizer compares, the same `nodes/proxy` precedent). Only meaningful for an identity `kube-apiserver`'s own RBAC recognizes (an OIDC claim mapped into its own OIDC config); a local `ui.auth.users[]` account is denied outright when this is on, since it has no real Kubernetes `User` to check. See `docs/guides/kairon-ui-console-rbac.md`.
- [x] Automatic cordon-triggered evacuation (first cut): `controller.cordonEvacuation.enabled` (opt-in, off by default) makes `kairon-controller` itself create a `MachineMigration` for every Machine on a Node whose `spec.unschedulable` transitions to true, mirroring KubeVirt's `LiveMigrateIfPossible` eviction strategy -- closing what was previously a real, documented gap ("no background/automatic drain triggered by `node.spec.unschedulable`"). Reuses the exact `MachineDisruptionBudget` throttling `kaironctl evacuate`/the admission webhook already share (`internal/controller/cordon.go`); a budget-blocked or already-attempted Machine is retried at most once per `controller.cordonEvacuation.minRetryInterval` (default `2m`), tracked via a `kairon.zyvor.dev/cordon-evacuate-attempted-at` annotation. `controller.cordonEvacuation.strategy` is `cold`/`auto` only -- deliberately never `live`, since automatic live migration triggered with no operator watching is a bigger step than automatic cold. See `docs/guides/machine-disruption-budgets.md`.
- [x] `MachineSet` (first cut): a Deployment/ReplicaSet-shaped abstraction -- `kairon-controller` creates/deletes plain `Machine` objects (`internal/controller/machineset.go`) to match `spec.replicas`, each built from `spec.template` (exactly a `Machine`'s own `spec`, validated the same way, not re-declared field-by-field in the CRD schema -- see `charts/kairon/crds/machinesets.yaml`'s use of `x-kubernetes-preserve-unknown-fields`). No `ownerReference`/garbage-collection (this project has none anywhere) -- owned Machines are found via a `kairon.zyvor.dev/machineset` label, the same name/label-reference pattern `MachineMigrationSpec.MachineName` already established for a single parent-child link. `RollingUpdate` (default, `maxUnavailable`-bounded, reusing `MachineDisruptionBudget`'s own `ParseIntOrPercent`) and `Recreate` rollout strategies both replace outdated replicas (tracked via a `kairon.zyvor.dev/machineset-template-hash` label) rather than editing one in place. Every owned Machine stays a completely ordinary Machine -- `kaironctl evacuate`, `MachineDisruptionBudget` selectors, everything else keeps working unchanged. Paced by count, not health: a rollout doesn't wait for a freshly created replacement to become `Running` before continuing, and there's no `maxSurge`, autoscaling, or pause/rollback primitive yet. See `docs/guides/machine-sets.md`.
- [x] `MachineInstanceType` (first cut): a reusable, named CPU/memory shape (`spec.resources`) a Machine references via `spec.instanceTypeName` instead of inlining `spec.resources` itself -- Kairon's equivalent of an EC2 instance type or KubeVirt's `VirtualMachineInstancetype`, deliberately kept to just the resource shape (no OS-preference bundling). `kairon-controller` resolves it into the Machine's own `spec.resources` exactly once (`internal/controller/instancetype.go`), the same "creation-time-only" convention `spec.image`/`spec.network.forwards` already use -- an explicit `spec.resources` always wins, and nothing downstream (hotplug, quota, the admission webhook, `kairon-node`) needs to know an instance type was ever involved once resolved. Relaxes `Machine.spec.resources`'s previously-required `cpu`/`memory` fields (now optional at the CRD-schema level, same relaxation `spec.image.path` already got for `spec.image.source`) since either `resources` or `instanceTypeName` may now supply them. Namespace-scoped only, no admission-time validation of the reference (an unresolvable name just stays unresolved rather than being rejected up front), no `kairon-ui` picker yet. See `docs/guides/machine-instance-types.md`.
- [x] NUMA topology, CPU set, and hugepages (first cut, qemu-only): `spec.resources.numaNode`/`.cpuSet`/`.hugepages` are direct passthroughs to FluxVM's own already-existing `CreateVmRequest` fields of the same name -- genuinely new plumbing on Kairon's side, not blocked upstream the way VFIO-through-live-migration was. `internal/fluxvm.Client.CreateWithVFIO` refuses the Machine outright with a clear error when any of the three are set and the resolved backend isn't `qemu`, rather than letting FluxVM silently ignore them the way it does for Cloud Hypervisor/Firecracker. **Not** exclusive host-core pinning -- `cpuSet` is a guest-visible vNUMA topology hint only; real host `cgroup cpuset.cpus` pinning exists in FluxVM (its own resize API) but allocating specific, non-overlapping host CPU numbers across competing Machines on one node is a real capacity-allocation problem `internal/scheduler`'s still-pure-count-based bin-packing doesn't solve, and remains a separate, bigger, not-yet-designed feature -- see `docs/guides/machine-cpu-numa.md`.
- [x] Windows guest support (first cut, honest scope): legacy-BIOS Windows Server/Windows 10 already works today with a pre-built image carrying VirtIO drivers and [cloudbase-init](https://cloudbase-init.readthedocs.io/) -- `spec.cloudInit` needs zero changes, since cloudbase-init consumes the exact same NoCloud datasource FluxVM's own cloud-init support already generates. `spec.security.secureBoot`/`.tpm` (previously dead fields -- accepted by the CRD, wired to nothing, doing nothing) are now refused outright at `CreateWithVFIO` with a clear error instead of a silent no-op: confirmed against FluxVM's own source, no backend Kairon talks to (QEMU, Cloud Hypervisor, Firecracker) implements UEFI/OVMF firmware or a vTPM device today, so Windows 11 (which hard-requires both) isn't supported -- a genuine FluxVM-side capability gap, tracked here the same way VFIO-through-live-migration names its own FluxVM dependency rather than reading as an unpicked Kairon TODO. See `docs/guides/machine-windows-guests.md`.
- [x] `MigrationPolicy` (first cut): scopes migration bandwidth defaulting and concurrency to Machines matching `spec.selector`, independent of the global `migration.maxConcurrentPerNode`/`maxConcurrentCluster` Helm values -- Kairon's namespace-scoped equivalent of KubeVirt's own `MigrationPolicy` CRD. Enforced by the existing migration reconcile loop's own admission check (`internal/controller/migrationpolicy.go`, mirroring `MachineDisruptionBudget`'s `LoadBudgetStates`/`AdmitDisruption` shape exactly) -- no admission webhook needed. `spec.maxConcurrent` blocks an over-cap migration into `Blocked`, retried automatically; `spec.bandwidthMbps` only fills in a `MachineMigration`'s own `spec.bandwidthMbps` when it's unset (an explicit per-migration value always wins), first-matching-policy-wins when more than one applies, deliberately not merged. See `docs/guides/migration-policies.md`.
- [x] Velero compatibility (verified, no plugin needed): a generic Velero backup/restore of Kairon's CRDs works with no Kairon-specific plugin -- confirmed by code review (not yet drilled live in this repo's own CI): no finalizer blocks a restore (Velero restore only ever `Create`s, never `Delete`s), a restored Machine re-adopts its FluxVM runtime automatically via the same reconcile-loop logic `runbook-backup-restore.md` already documents, and every Kairon `Patch*` call is a scoped JSON merge patch that never wipes Velero's own tracking labels. One real, named gap: Velero's standard CSI-snapshot mechanism cannot back up disk content for either storage path Kairon supports today (`hostPath`/`local` PVs aren't real CSI volumes; Kairon's own iSCSI CSI driver has never implemented `CreateSnapshot`/`DeleteSnapshot`) -- the exact same limit `MachineSnapshot` already has, not a new one. See `docs/runbook-velero-backup.md`.
- [x] `kubectl-kairon` plugin (first cut): `kubectl kairon ...` now works identically to `kaironctl ...`, via a real second binary (`cmd/kubectl-kairon`) sharing kaironctl's exact command dispatch -- `kaironctl`'s own `run()` was factored out into an importable `internal/kaironctl` package (`Run(args, version)`) so both binaries call the same code, rather than one shelling out to the other. This works because kubectl already invokes a plugin binary with the subcommand as its own `os.Args[1:]` (`kubectl kairon evacuate worker-1` runs `kubectl-kairon evacuate worker-1`), exactly the argument shape `kaironctl`'s dispatch already expected -- no argument translation needed. Pure ergonomics, no new backend surface; not shipped as a container image, matching `kaironctl` itself.
- [x] VM export (documented, deliberately not new Kairon machinery): getting a Machine's disk content out of the cluster entirely (cross-cluster clone, off-site backup) is standard Kubernetes tooling -- a short-lived Pod mounting the same `PersistentVolumeClaim` read-only, `kubectl cp`/pushed to object storage -- not a new Kairon-specific export server/ticket mechanism. Kairon has no Pod/Job/Service creation anywhere (`kairon-node` never runs a Machine inside a Pod at all), and building bespoke export infrastructure would only duplicate what a one-off Pod already does, at the cost of real new API surface (Pod scheduling, Service exposure, its own RBAC) this project doesn't otherwise need. See `docs/runbook-vm-export.md`.
- [x] Image import (first cut): `spec.image.source.httpURL` (opt-in via `node.imageCacheDir`, off by default) has `kairon-node` itself download a remote qcow2/raw image URL into a node-local, digest-keyed cache instead of requiring an operator to have already placed a file at `spec.image.path` -- closing Kairon's most direct gap against KubeVirt's CDI importer. `spec.image.digest` (already existing) becomes the mandatory cache key, so every Machine naming the same digest shares one download. No format conversion (FluxVM already consumes qcow2/raw directly, so bytes are trusted via digest, not inspected), no OCI/registry references, no cache eviction -- see `docs/guides/machine-image-import.md`.
- [x] Guest exec (first cut): a `Running` Machine with `spec.guestAgent.enabled` gets an **Exec** button in `kairon-ui`'s dashboard -- run a one-shot command (or PowerShell one-liner for Windows guests) inside the guest with no SSH key, console, or network path into the guest required. This wraps FluxVM's real `POST /v1/vms/{id}/qga/exec` (qemu-guest-agent guest-exec, with FluxVM doing its own guest-exec-status polling internally -- Kairon only ever sees one synchronous request/response) via the exact same `kairon-ui` &harr; `kairon-node` relay infrastructure the VNC console already established (`internal/consoleproxy`), just a plain JSON POST instead of a WebSocket byte relay. No new spec field, no new guest-image dependency -- reuses the same channel `spec.guestAgent` already provides for guest-IP resolution and `MachineSnapshot` quiesce. Gated more strictly than the console though: requires an admin account outright (no per-Machine allowlist opt-out yet), and there's no command-line audit trail by design (arguments can carry secrets) -- see SECURITY.md's "Guest exec" section and `docs/guides/machine-guest-exec.md`. One-shot only, no interactive shell -- see the text console entry below for that.
- [x] Interactive text console (first cut): `spec.guestAgent.console` opts a Machine into FluxVM's own vsock-based interactive shell (`GET /v1/vms/{id}/console`, Kairon's `virtctl console` equivalent), rendered in-browser via xterm.js -- `kairon-ui` &harr; `kairon-node` &harr; FluxVM, reusing the exact same ticket-issuance, per-Machine authorization, and `KAIRON_NODE_CONSOLE_TOKEN`/`console.tls` trust chain the VNC console already established, just a `kind=text` ticket dialing a different `internal/consoleproxy` route (kairon-node as a *client* dialing FluxVM's own WebSocket console endpoint, rather than a Unix socket it dials directly the way VNC's QEMU display works). Independent of `spec.guestAgent.enabled` (standard `qemu-guest-agent`) -- this is a completely different, FluxVM-**proprietary** channel requiring FluxVM's own `fluxvm-guest-agent` binary and systemd service baked into the guest image, a genuinely new operational dependency this project has never asked of users before. Works on every backend (unlike VNC, QEMU-only), since FluxVM's vsock agent isn't tied to a display device; the in-guest token itself is entirely FluxVM's own to generate and inject, never touched by Kairon. See SECURITY.md's "Text console" section and `docs/guides/machine-text-console.md`. No resize-after-connect, no session persistence/reconnect, and the xterm.js bundle is lazy-loaded in the dashboard so it never costs anything for a deployment that doesn't use this feature.
- [x] Live host resource limits (first cut): `spec.resources.limits` (`cpuQuotaPercent`/`memoryMaxBytes`/`ioWeight`/`pidsMax`) is a real, kernel-enforced cgroup v2 cap on a running Machine's own VMM process -- FluxVM's `POST /v1/vms/{id}/resources`, backend-agnostic (unlike `hugepages`/`numaNode`/`cpuSet`, this isn't QEMU-only, since it operates on the cgroup the VMM process runs in, not a backend-specific API). Distinct from `spec.resources.cpu`/`.memory` (what the *guest* sees) and from CPU/memory hotplug (which grows what the guest sees, one-way only): this is a host-side ceiling, reconciled continuously and freely raisable-or-lowerable at any time, closing a real gap versus KubeVirt (whose VMs get Kubernetes' own Pod resource `limits` enforcement for free; a Kairon Machine, running outside a Pod entirely, previously had no host-side enforcement at all beyond the scheduler's bin-packing count). Deliberately excludes FluxVM's own `cpuset_cpus` cgroup control -- the same real capacity-allocation problem already named in `spec.resources.cpuSet`'s own doc comment (allocating specific, non-overlapping host cores across competing Machines needs a scheduler capacity model this project doesn't have). See `docs/guides/machine-resource-limits.md`.
- [x] Configurable hotplug headroom (first cut): `spec.resources.maxCpu`/`.maxMemory` request more CPU/DIMM hotplug headroom than FluxVM's own default (roughly double `cpu`, and `memory + 2Gi` or double, whichever is larger) -- a real, previously self-documented gap (`docs/guides/machine-hotplug.md` said outright "not yet configurable from Kairon"; FluxVM's own `CreateVmRequest.max_vcpus`/`.max_memory_mib` already existed and were simply never plumbed through). Creation-time-only, like `cpu`/`memory`'s own boot-time sizing -- the headroom is baked into the VM's boot-time `-smp`/`-m` arguments (`maxcpus=`/`maxmem=`) and can't be grown on an already-running Machine at all, so this doesn't lift `CPU/memory hotplug`'s own "bounded by headroom reserved at creation" limit, it just lets that fixed ceiling be set higher upfront. FluxVM silently clamps `maxCpu` up to at least `cpu` if set too low (never an error); a `maxMemory` below `memory` is FluxVM/QEMU's own inconsistent-argument error to raise, not something Kairon validates first. See `docs/guides/machine-hotplug.md`.
- [x] `spec.cloudInit.writeFiles` (first cut): drops a file into the guest before first boot via cloud-init's own `write_files` module -- e.g. a systemd unit or an app config, no custom image build needed. Another previously self-documented gap: FluxVM's own `CloudInitSpec.write_files` already existed (`internal/fluxvm.CloudInitSpec`'s own doc comment said outright "not yet surfaced here") and was simply never plumbed through. Same creation-time-only posture as the rest of `spec.cloudInit`. See `docs/guides/machine-network.md`'s "Cloud-init guest customization" section. No `kaironctl create` flag yet -- YAML/kubectl only, matching how most multi-field `cloudInit` entries already work.
- [x] Guest file access (first cut): a `Running` Machine with `spec.guestAgent.console` gets a **Files** button in `kairon-ui`'s dashboard -- read or write a file inside the guest at runtime, no SSH key or shared volume needed. Wraps FluxVM's own bespoke vsock guest agent (`POST /v1/vms/{id}/agent/put-file`/`agent/get-file` -- the same channel and guest-image dependency, `fluxvm-guest-agent`, the interactive text console needs; a completely different channel from guest exec's `qemu-guest-agent`), relayed through the same `internal/consoleproxy` infrastructure as a plain JSON request/response, the same shape guest exec already has. Admin-only, same posture as guest exec (stricter than the text console's any-operator default) -- arbitrary guest file read/write is at least as sensitive as arbitrary command execution. No path allowlist/denylist, and reads are capped at kairon-ui's own ~3MB effective ceiling (base64 inflates a 4MiB HTTP-response limit) -- a larger file fails to decode with a clear error rather than returning truncated content. See SECURITY.md's "Guest file access" section and `docs/guides/machine-guest-agent-files.md`.
